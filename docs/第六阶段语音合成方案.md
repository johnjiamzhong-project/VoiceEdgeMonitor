# Phase 6 TTS

## Boundary

The TTS stage is an optional process. It does not change the Phase 1 video
publisher or the Phase 2 microphone/ASR process:

```text
Qwen3-VL answer
  -> Unix datagram
  -> edgesight_tts
  -> sherpa-onnx Offline TTS
  -> ALSA playback
  -> board speaker
```

When the complete pipeline is running, TTS also publishes a timestamped,
16 kHz far-end reference at `/tmp/edgesight-aec-reference.sock`. The audio
listener uses this reference for target-board SpeexDSP echo cancellation while
keeping the microphone open during the acknowledgement. This is a local
runtime socket and is not a model or credential asset.

The video worker sends answer data with non-blocking Unix datagrams. During
normal operation, the RKLLM callback forwards each complete sentence as soon
as it is available; a raw full-answer datagram remains as the compatibility
fallback if streaming cannot be started. If the TTS socket is unavailable,
the worker emits `tts_request_failed` and keeps the vision result successful.
The TTS process accepts one request at a time and emits `tts_rejected
reason=busy` for a concurrent request rather than building an unbounded audio
queue. Within an accepted request, sentence-ending Chinese or ASCII
punctuation is used to split the text into bounded segments. The service
synthesizes ahead into a small queue while one persistent ALSA session plays
completed segments, so the first sentence can start before the complete answer
has been synthesized.

### LLM-to-TTS sentence streaming

The reserved datagrams below are internal protocol messages. Ordinary text
datagrams are still accepted for one-shot compatibility:

```text
__edgesight_tts_stream_begin__:<first complete sentence>
__edgesight_tts_stream_segment__:<next complete sentence>
__edgesight_tts_stream_end__
```

Streaming control datagrams use a bound Unix sender and require an explicit
TTS acknowledgement. A full two-segment input queue returns a retry response;
the vision worker applies bounded backpressure and does not advance to
`stream_end` until every segment has been accepted. This avoids silently
dropping the tail when local `sendto()` succeeds but the TTS queue is full.

`VisionWorker` accumulates RKLLM callback chunks until a Chinese or ASCII
sentence boundary, then sends the first sentence with `stream_begin` and later
sentences with `stream_segment`. It sends `stream_end` after RKLLM completes.
The TTS service keeps at most two not-yet-synthesized stream segments, accepts
subsequent datagrams while synthesis/playback is running, and rejects a new
stream while another request is active. This overlaps language generation,
TTS synthesis, and playback without introducing an unbounded queue.

## Build

On the target board:

```bash
cmake -S . -B build-tts \
  -DEDGESIGHT_BUILD_STREAMER=OFF \
  -DEDGESIGHT_BUILD_AUDIO=OFF \
  -DEDGESIGHT_BUILD_TTS=ON \
  -DSHERPA_ONNX_ROOT=/home/firefly/opt/sherpa-onnx-v1.13.4-linux-aarch64-shared-cpu \
  -DBUILD_TESTING=ON
cmake --build build-tts --parallel
ctest --test-dir build-tts --output-on-failure
```

The repository deployment layout uses `build-rk3588/edgesight_tts`. The
checked-in launcher supplies the external model paths:

```bash
scripts/run_tts.sh
```

The default playback device is `plughw:0,0`. The board's raw `hw:0,0` device
requires two playback channels, so the `plughw` layer is intentionally used to
convert the generated mono 44.1 kHz PCM to the ES8323 playback format.

On the Firefly board, the ES8388/ES8323 3.5 mm path also requires the codec
output pins and headphone switch to be enabled. The checked-in launchers apply
this mixer state before TTS starts:

```bash
scripts/init_audio_output.sh
```

It enables `Headphone`, `hp switch`, `OUT1`, and `OUT2`, and disables the
separate `Speaker`/`spk switch` path. The settings are reapplied whenever
`run_tts.sh` or `acceptance_tts.sh` starts, so a board reboot does not leave
the application path muted. Override with `EDGESIGHT_AUDIO_OUTPUT_INIT=false`
to skip this board-specific setup.

## One-shot and service checks

Generate and play a Chinese sentence once:

```bash
scripts/acceptance_tts.sh
```

For the application path, start `scripts/run_tts.sh` and enable the matching
socket in the streamer configuration:

```yaml
vision:
  enabled: true
  socket: "/tmp/edgesight-vision.sock"
  vision_model: "/home/firefly/EdgeSightAssistant/vision-smoke-v1.2.3/qwen3-vl-2b-vision_rk3588.rknn"
  llm_model: "/home/firefly/EdgeSightAssistant/vision-smoke-v1.2.3/qwen3-vl-2b-instruct_w8a8_rk3588.rkllm"
tts:
  enabled: true
  socket: "/tmp/edgesight-tts.sock"
```

The target-board probe can also validate the worker-to-TTS interface without
changing the real RTMP configuration:

```bash
build-rk3588/edgesight_vision_worker_probe \
  /tmp/edgesight-vision-moon.ppm \
  /home/firefly/EdgeSightAssistant/vision-smoke-v1.2.3/qwen3-vl-2b-vision_rk3588.rknn \
  /home/firefly/EdgeSightAssistant/vision-smoke-v1.2.3/qwen3-vl-2b-instruct_w8a8_rk3588.rkllm \
  /tmp/edgesight-vision.sock \
  "请简短描述图片内容。" \
  --tts-socket /tmp/edgesight-tts.sock
```

The authoritative events are:

```text
vision_first_token monotonic_ms=... bytes=...
vision_first_sentence monotonic_ms=... bytes=...
vision_finished monotonic_ms=... answer="..."
tts_request_sent bytes=... monotonic_ms=...
tts_request_accepted monotonic_ms=... bytes=...
tts_started monotonic_ms=... text="..."
tts_segment_synthesized index=1 total=... bytes=... synthesis_ms=...
tts_playback_started monotonic_ms=...
tts_segment_playback_started index=1 monotonic_ms=...
tts_segment_finished index=1 playback_ms=...
tts_finished monotonic_ms=... samples=... sample_rate=... \
  segments=... synthesis_ms=... playback_ms=... elapsed_ms=... playback=enabled
```

For a streamed request, `tts_request_accepted`, `tts_started`, and
`tts_playback_started` can occur before `vision_finished`. The additional
`tts_segment_accepted`, `tts_segment_synthesized`,
`tts_segment_playback_started`, and `tts_stream_end_received` events expose
the overlap and queue boundaries. `vision_first_token` is emitted by the
vision worker on the first non-empty RKLLM callback, while the legacy-named
`vision_first_sentence` event is emitted after the first TTS phrase/safe-length
segment has been sent as `stream_begin`. The first segment uses a sufficiently
long Chinese/English comma boundary when available, or a 12-character UTF-8
fallback; if that fallback lands on a closing quote/bracket, it waits for one
more UTF-8 codepoint so a final `。` or `！` is not synthesized as a standalone
segment. Later segments retain sentence-level boundaries.

The streaming TTS service keeps two bounded queues: at most two input segments
awaiting synthesis and at most two synthesized segments awaiting playback. A
producer synthesizes the next segment while the persistent ALSA session plays
the current one. This removes the avoidable serialize-synthesize-then-play gap;
an unusually short first phrase can still leave a small gap when its audio is
shorter than the next VITS synthesis time.

Audio activation events also include the same Linux monotonic clock field. The
`monotonic_ms` values are comparable across the audio, vision, and TTS
processes, so latency can be calculated as `asr_final → vision_started →
vision_finished → tts_playback_started`; `tts_finished` marks the end of
physical playback. `tts_playback_started` is emitted for the first segment;
the segment events show later boundaries. `synthesis_ms` is the sum of segment
synthesis times and `playback_ms` includes the final ALSA drain.

The full video + audio + vision + TTS concurrent acceptance was completed on
the target board on 2026-08-14. During TTS playback, the video and audio
processes remained active; the final video statistics were about 29.9 FPS with
zero publisher errors, and the TTS log confirmed `playback=enabled`.
